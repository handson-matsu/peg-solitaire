# English board ペグソリティア問題生成・調査

標準33穴の盤面で、中央 `(3,3)` の1個から逆向きの合法手だけを使って配置を生成します。外部の問題集・192問のデータ・既知の解法は使用していません。同じ生成済みデータを使う静的Webアプリも含みます。

## Webアプリを遊ぶ

リポジトリ直下の `index.html` がゲームです。ビルドや外部APIは不要です。問題は既存の `generated-puzzles.json` のみを読み込み、解法・難易度のデータはUIに読み込みません。5〜32個を選べ、直前と同じ問題を避けて出題します。

ローカルで確認する場合：

```sh
python3 -m http.server 4173
```

ブラウザで `http://localhost:4173` を開きます。JSON取得にHTTPを使うため、HTMLファイルの直接ダブルクリックではなく、この方法を使ってください。

### GitHub Pagesで公開する

1. このフォルダのファイルをGitHubリポジトリの公開対象ブランチにコミットしてpushします。
2. リポジトリの **Settings → Pages → Build and deployment** を開きます。
3. **Source: Deploy from a branch** を選び、対象ブランチと **/(root)** を指定して保存します。
4. Pages設定に表示されるURLから遊べます。

全参照は相対パスなので、リポジトリ名を含むURLでも動作します。`.nojekyll` を同梱しています。公開時に最低限必要なファイルは `index.html`、`styles.css`、`app.js`、`game-core.js`、`favicon.svg`、`generated-puzzles.json`、`.nojekyll` です。生成・解析ファイルを削除する必要はありません。

公開設定の参考：[GitHub公式ドキュメント](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)。この実装作業ではGitHubへのpushや公開設定の変更は行っていません。

### ゲーム操作

ペグをタップして選び、輪が表示された空き穴をタップするとジャンプします。黄色が選択中のペグです。キーボードでもTabとEnter/Spaceで操作でき、Escapeで選択を解除できます。

- **1手戻す**：何手でも戻せます。クリア・行き詰まりの後も使用できます。
- **リセット**：今の問題の初期状態に戻します。
- **別の問題**：同じペグ数から直前と異なる問題を選びます。
- **ペグ数を変更**：選択画面に戻ります。次のスタートで新しい問題を始めます。

中央1個のみをクリアと判定します。合法手がない場合は行き詰まりを表示し、UNDOとリセットを引き続き使えます。ゲーム状態はページ内で保持するため、ページの再読み込みでは開始画面に戻ります。

## 問題生成の実行

C++17対応のコンパイラと、検証用のPython 3を使用します。外部ライブラリは不要です。

```sh
c++ -O3 -std=c++17 -Wall -Wextra -pedantic generator.cpp -o generator
./generator
python3 verify.py
```

カレントディレクトリに次の3ファイルを出力します。同名ファイルは上書きします。

- `generated-puzzles.json`：5〜32個の各ペグ数につき最大100問
- `generated-solutions.json`：各問題に対応する正解手順
- `generation-report.txt`：設定、探索時間、展開数、各層の発見数、完全探索かサンプリングか

今回保存した結果を再生成するコマンド：

```sh
./generator --width 5000000 --seconds 120 --seed 20260921 --max-expansions 100000000
python3 verify.py
```

## 探索方法と上限

盤面は `uint64_t` の33ビットで表します。通常手の出発点・飛び越す穴・到着点をあらかじめ列挙し、逆手では「到着点だけにペグがある」ときに3ビットを反転します。

ペグ数ごとの幅優先探索で、回転4通りと反転を含むD4群の8変換の最小ビット列を重複除去キーにします。中央の目標はすべての変換で不変なので、各対称クラスの代表1個から展開するだけで、完全探索時にはすべてのクラスを得られます。

層の候補が探索幅を超えた場合、シード付きハッシュ順位で異なるクラスを選択します。単一のランダムウォークと違い、多数の配置を並行して次の層へ進めます。ただし一様な全問題サンプリングを保証するものではありません。間引いた後の発見数は下限であり、0でも解ける配置が存在しない証明にはなりません。

| オプション | 既定値 | 意味 |
|---|---:|---|
| `--width` | 200000 | 各層に保持する中間配置数（最大10000000） |
| `--seconds` | 120 | 探索の時間上限（最大3600秒） |
| `--max-expansions` | 100000000 | 展開する親配置数の上限 |
| `--seed` | 20260921 | 間引きに使うシード |

保存枠100問と中間配置の探索幅は別です。100問集まった層でも、より多いペグ数の問題を作るために展開します。候補の重複除去と全層の親リンクをメモリ上に保持するため、探索幅を大きくするとメモリ使用量も増加します。既定値は小さめの20万です。

時間は親配置1,024個ごとに確認します。層の候補選択・JSON保存にかかる時間は別途必要なため、壁時計上の厳密な終了期限ではありません。展開回数の上限は各配置で確認します。上限に到達しても、そこまでの問題と解法を出力します。未到達のペグ数は空配列と `not reached` を記録します。

## JSONとヒントへの利用

問題の座標は0始まりです。問題番号は付けません。

解法は同じキー・同じ配列位置の問題に対応します。例えば `solutions["27"][i]` は `puzzles["27"][i]` の解法です。各手は次の形式です。

```json
{"from": [1,3], "over": [2,3], "to": [3,3]}
```

各問題にはペグ数−1手が含まれます。各手を配列の先頭から通常ルールで実行すると中央1個になります。生成時の各配置に親配置と逆手を記録し、そのリンクをたどって通常手順を復元しています。盤面の向きを保持するため、問題と手順の座標はそのまま対応します。

ヒント機能では、この解法に沿って進んでいる場合に次の手を表示できます。別の手で進んだ局面に対するヒントには、その局面からの解法探索などが別途必要です。

## 検証

`python3 verify.py` は保存した全問について、盤面とペグ数、各層100問以下、D4重複なし、手順の長さ、全手の合法性、最終配置が中央1個であることを独立した座標ベースの処理で検証します。Pythonの `-O` は付けずに実行してください。

## 難易度解析

既存の問題・解法JSONを変更せず、全2,498問を共通尺度で評価します。

```sh
python3 analyze-difficulty.py
python3 verify-difficulty.py
```

`difficulty-analysis.json` と `difficulty-report.txt` を出力します。Python標準ライブラリとC++17のみを使い、一時ディレクトリで解析エンジンをコンパイルします。`generator.cpp` の盤面・対称性処理だけを再利用し、問題生成処理は呼び出しません。

解析は中央から逆到達可能な全クラスをペグ数順に列挙し、通常手の動的計画法で解法数と統計を計算します。2層分のみを保持しますが、数百万局面を扱うため数百MB〜1GB程度以上の空きメモリを見込んでください。既定の探索時間上限は180秒（`--seconds`で変更）。時間切れは不完全な判定を罠とみなさず、エラー終了して既存の最終解析ファイルを残します。出力処理とコンパイルの時間は別です。

JSONの `puzzles` 配列に各問の指標があります。`pegCount` と0始まりの `puzzleIndex` が元の問題・解法配列との対応を示し、`board` には元の配置をそのまま保存します。`metadata` には入力SHA-256、尺度の定義、全体統計、暫定境界を記録します。

- `legalFirstMoves` / `winningFirstMoves`：初手の合法手数／中央まで解ける手数
- `solutionCount`：10^18で飽和する整数文字列。`solutionCountCapped` が真なら下限値
- `solutionCountLog10` / `solutionCountApprox`：巨大な解法数も比較できる浮動小数点の近似指標
- `averageLegalMoves` / `averageWinningMoves`：正解ルート上の平均合法手数／正解手数
- `trapMoveRate`：正解ルート上の局面ごとの罠率の平均
- `forcedMoveRate`：正解手が1本だけの局面の割合
- `forcedWithAlternativesRate`：罠があり、正解手が1本だけの局面の割合
- `savedSolutionMetrics`：元の保存済み解法1本に沿った統計

ルート平均は「各局面で正解手を一様に選ぶ」方策について全正解分岐から計算した期待値です。完成した全解法を等確率で抽出するものではありません。中央1個の終端局面は平均に含めません。解法数は座標付きの手順の数であり、対称な手順や異なる順序も数えます。

### 評価式と採用理由

`L` を合法手数、`W` を正解につながる手数とします。

- `P`：全合法手を一様に選んでプレイした場合の中央クリア確率
- `B`：正解ルート上の `log2(L/W)` の合計の期待値
- `F`：正解ルート上の「W=1かつL>1」の局面数の期待値

```text
D = 0.6 × (-log2(P)) + 0.3 × B + 0.1 × F
difficultyScore = 100 × (1 - exp(-D / 12))
```

`P` は解法の広さと合法手の分岐をまとめて評価し、`B` は解く途中で必要な選択の厳しさ、`F` は罠の中で唯一の正解を選ぶ局面を補足します。ペグ数自体は加点しません。長くてもすべての手が安全なら0で、難しい判断が続けば負荷が累積します。単なる解法数の大小だけでは、選択肢に対する正解の割合がわからないため、この組み合わせを使います。

係数と表示変換の定数12は暫定値です。人間の先読み能力や定石の知識を測ったスコアではなく、人間の成功確率でもありません。今回の到達判定と解法数DPは全探索ですが、難易度評価式はプレイ時間・失敗回数・ヒント使用率による校正が必要です。

★の参考境界は全問共通の60と80です。各問の分類は確定していません。分布や候補境界の件数、ペグ数別統計、詳細な定義は `difficulty-report.txt` にあります。ペグ数ごとの3等分は行いません。

`verify-difficulty.py` は全問の元データとの対応、SHA-256、初手の合法手数、保存解法の平均合法手数、評価式を検証します。さらに5〜7個の239問を、対称性やビット盤面を使わない独立した順方向全探索と照合します。
